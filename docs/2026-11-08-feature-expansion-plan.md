**1. 建议定位与目标用户**

建议将 GitHubSP 定位为：**面向用户和 Agent 的 GitHub Release 下载与持续关注工具**。

桌面端提供选择、确认、查看进度和管理文件的工作台；Agent 端提供可组合的结构化工具。两端共享项目规则、下载队列和处理记录。

优先服务两类用户：经常从 GitHub 获取软件、希望省去反复选附件与检查更新的 Windows 用户；需要下载工具链、准备工作环境或获取项目更新信息的本机 Agent 用户。Agent 首个目标宿主为 DeepSeek Harness，后续通过 MCP 扩展到其他 Agent。

下一阶段以公开 GitHub 仓库、Windows、本机 Agent 为边界。私有仓库、自动安装、跨平台客户端和云端下载另行评估。

**2. 当前基础与调研判断**

当前基线为 v0.3.1：Tauri + React + Rust，已有下载队列、暂停恢复、Release 浏览、批量直链、历史、收藏检查、未读提醒、独立关注规则、自动入队、线路检测与备份。附件匹配、API 限流处理和可选 SHA-256 校验也已有基础，应按增强功能规划。

规划时运行服务由桌面宿主管理，同一数据目录有单实例约束；当时文档列出真实网络完整下载、干净系统安装和部分原生交互等缺项，GitHub Actions 主要覆盖历史 Slint 入口。本轮补齐网络与相关原生交互证据、新增 Tauri CI，系统环境缺项仍保留。

相关事实以 [README](../README.md)、[桌面架构](tauri-desktop.md)、[数据与存储](data-storage.md) 和当前源码为准。

调研表明，基础操作已有成熟替代：GitHub CLI 能下载 Release 附件；官方 GitHub MCP 能查询 Release、管理 Star/Watch；gh-release-mcp 和 Gopeed 已公开下载相关 MCP 能力。方案的价值假设是：**更稳定地选对附件、完成长下载，并在不同对话之间保留关注和处理状态**。该假设仍需使用验证。

**3. 贯穿两端的关键场景**

| 场景 | 桌面端体验 | Agent 端体验 |
| --- | --- | --- |
| 获取一个软件或工具 | 选择项目与版本，看到推荐附件及理由，确认下载 | 解析候选附件，提交任务，取得路径、版本和校验结果 |
| 持续获取常用项目 | 保存架构、安装版/便携版及更新偏好 | 按用户指令保存关注规则，读取后续更新与下载结果 |
| 查看近期变化 | 在更新中心按项目和时间浏览，逐项处理 | 读取自上次游标之后的更新，生成带来源的简报 |
| 管理已下载文件 | 查看项目、版本、文件位置和本地存在状态 | 查找已经下载的目标，避免无意义的重复获取 |

**M0：可靠性与发布基础**

- 统一限速保存、设置输入和队列显示的单位，保留旧数据的解释与兼容。
- 为当前 Tauri 入口建立 CI，覆盖项目要求的相关测试、前端构建及分发检查；历史入口保留其既有定位。
- 验证真实 Release 下载、暂停后重启、失败恢复、目录不可写、重复目标以及已有校验失败路径。
- 在可用测试环境中验证安装版、免安装版及缺失 WebView2 的行为。缺少相应环境时，明确保留未验收项。

验收：可复现的真实文件下载与哈希对照；旧数据可加载；限速显示与输入一致；当前入口有独立 CI 证据。环境缺项不能计为通过。

**M1：项目下载偏好与网络设置**

- 每个项目保存目标系统、架构和安装版/便携版偏好，保留现有通配符与 `{version}` 规则。
- 展示匹配到的附件、命中理由及不确定项；无匹配或存在歧义时返回待选择状态。
- 下载预览固定实际版本与附件身份，避免将后续变化的 `latest` 当作同一目标。
- 增加“直连/系统代理/自定义代理”的明确选择，并区分元数据查询与附件下载的测试结果。首批支持的代理协议在实现设计时确定。
- 可选增加仅用于公开仓库元数据访问的 GitHub 认证；凭据不进入普通备份、日志或公共镜像请求。私有仓库不随此项自动纳入范围。

验收：安装版与便携版、x64 与 ARM64、通用包及未知命名样本均有明确选择结果；歧义不会自动选错；旧收藏规则兼容；代理关闭后行为可解释。认证若纳入本批，单独验证凭据保存和请求边界。

**M2A：DeepSeek Harness 原生插件**

首版目标是 Windows 上同机运行的 DeepSeek Harness。通过 Cordis 原生插件注册可由模型调用的工具，并接入宿主的工具结果呈现与插件生命周期；本阶段不先启动 MCP 服务再让插件转接。

插件通过受控本机接口调用 GitHubSP，复用 Rust 核心。首版仍建议连接正在运行的 GitHubSP 桌面/托盘进程，由桌面进程作为队列和数据库的唯一执行者。是否前置独立无界面运行仍是待审阅项。

首版工具按用户任务组织，具体名称在接口设计时确定：

| 工具能力 | 首版行为 |
| --- | --- |
| 解析 Release 与附件 | 输入仓库或 Release 地址，返回固定版本、候选附件、匹配理由和不确定项 |
| 创建下载 | 基于已解析的目标创建任务，返回任务 ID；相同幂等请求不会重复创建 |
| 列出/查询任务 | 返回状态、进度、失败原因及完成结果；支持找到之前创建的任务 |
| 等待状态变化 | 有界等待，超时返回当前状态；等待结束不等于取消任务 |
| 控制任务 | 复用暂停、继续和取消能力；首版不暴露删除成品文件 |
| 使用现有关注能力 | 读取收藏、创建或调整既有关注规则、触发检查并读取当前更新状态；增量更新记录留到 M3 |

完成结果至少包含仓库、固定版本、附件名、实际路径、文件大小和校验状态。有官方摘要并匹配、仅计算本地哈希、没有可用摘要和校验失败应明确区分。

生命周期与权限规则：

- Harness 会话结束或插件停用后，已接受任务继续由 GitHubSP 执行；桌面进程退出时沿用保存/暂停流程，退出后不继续检查或下载。
- GitHubSP 未运行时返回明确的启动提示；首版不静默启动常驻服务。
- 服务重启后按任务 ID 恢复查询，续传行为沿用已验证的恢复规则；不盲目重放创建请求。
- 多个 Harness 会话与桌面操作进入同一队列，复用既有串行调度；禁止各自启动引擎并直接操作同一数据目录。
- 文件写入限定在用户配置的允许目录；范围外目录返回明确错误。首版文件操作止于下载，不执行下载的文件。
- 插件加载、重载和停用应正确注册或注销工具及释放监听，不重复注册、不把任务绑定到单次模型调用。队列状态归 GitHubSP 所有。

验收：以实际安装的 DeepSeek Harness 版本为基准，记录支持范围，在真实宿主中完成工具发现、解析、下载、查询、暂停/继续和现有关注规则操作。验证重试调用不重复建任务、新会话能查询已有任务、桌面与多个会话共用队列、服务未运行及目录越界的错误，以及插件重载/停用后的资源释放。真实网络使用明确授权的公开测试附件。

进入 M2B 的门槛：上述关键路径真实验收通过，完成“获取工具”“中断后恢复”“保存并再次使用关注规则”三个场景的重复使用检查，且没有未解决的阻塞性功能问题。已知限制应明确记录。模型自然语言回复或模拟工具检查不能代替真实宿主与下载证据。

M2A 的成功指标同时与宿主现有 Shell/CLI 路径对照：用户需要介入的次数、正确选附件的情况、遇到中断后的恢复成本、是否能取得明确结果。若收益不明显，先修正原生插件，再决定扩大接入面。

**M2B：将已验证能力封装为 MCP**

本阶段在 M2A 验收通过后开始。将已稳定的操作和结果封装成标准 MCP 工具，通过本地 stdio 供 Codex、Claude Code 等其他 Agent 接入。

- MCP 适配器调用与原生插件相同的 GitHubSP 服务，复用目标解析、任务 ID、幂等、状态与错误语义，不重新实现下载和关注逻辑。
- MCP 不依赖 DeepSeek Harness 进程或模型推理；其他 Agent 无需安装或启动 Harness。原生插件与 MCP 是同一服务的不同入口。
- 首版复用 M2A 的 GitHubSP 运行条件、允许目录和队列所有权。MCP 连接启停不改变已接受任务的生命周期。
- 提供安装、连接、工具发现、失败诊断和卸载说明。远程/云端 Agent 不在本阶段接入承诺中。

验收：至少在 Codex 和 Claude Code 两个宿主完成 M2A 已验证的核心场景，并对照原生插件确认结果一致；验证 MCP 调用超时、断连、重连查询和重复创建请求，以及原生插件、MCP 和桌面同时操作共享队列的情况。

**M3：更新中心与 Agent 关注能力**

- 在收藏基础上增加分组、标签、按项目/时间浏览的更新记录和完整 Release 说明。
- 区分“已看到”“忽略此版本”和“已下载”，减少重复提醒；保留记录，不把读取列表直接算作用户已读。
- 支持每项目的稳定版/预发布规则，以及仅提醒/自动下载选择。自动下载是显式配置，沿用 M1 的附件选择约束。
- 在 M2A 的现有关注工具基础上，为 Harness 原生插件增加增量更新读取及显式确认处理结果；新能力先在原生插件验证，通过后再同步到 MCP。
- 增量读取采用可重试的游标；读取失败或重复读取不吞掉更新。新建关注时记录基线，不将全部历史版本当作新增。
- GitHubSP 内的“关注”默认是本地规则，与 GitHub Star/Watch 分开标识。本批不写入用户远程 Star/Watch。

验收：一次发布只产生一个可追踪事件；服务重启后状态保留；跨端读取和确认不丢事件；限流及降级时能说明附件信息是否完整；无歧义才自动入队。先完成桌面与 Harness 插件验证，再验证 MCP 结果一致。版本是否值得更新的摘要可由外部 Agent 生成，核心检查不依赖模型调用。

**M4：轻量软件库与工作流分发**

- 将项目、Release、下载任务和本地文件关联，展示最新发现版本与已下载版本的差异。
- 展示文件存在、缺失或位置变化，不将“已下载”标为“已安装”。首版不扫描系统安装清单。
- 提供不含凭据和机器绝对路径的关注清单导入导出；导入时选择保存根目录，并预览合并、重复与冲突处理。应用备份与关注清单保持不同用途。
- 围绕已验证场景完善 Harness 插件的工作流引导，例如“下载工具链”“检查关注更新”“生成更新简报”。
- 在已稳定的 MCP 基础上，为其他宿主提供 Skills 和可选插件包装，完善安装、升级及接入说明；不将初次开发 Harness 原生插件推迟到本阶段。

验收：文件缺失不会显示可用；清单迁移后需重新确认本机目录；目标宿主的新会话能按说明发现并正确调用工具；其他宿主的插件包装与直接 MCP 接入得到一致结果。

**5. 后续候选与进入条件**

| 候选方向 | 进入条件 |
| --- | --- |
| 独立无界面运行 | M2A 证明 Agent 场景有效，且用户确实需要关闭桌面窗口/进程后持续执行；再拆出可独立启动的唯一工作进程，并验证与 GUI 的所有权交接 |
| 浏览器发送到 GitHubSP | 频繁复制链接成为主要阻力；先考虑链接唤起，再评估浏览器扩展 |
| 多任务并发与更多分段 | 真实下载数据证明现有串行任务调度是瓶颈；先定资源上限与恢复语义，再修改引擎 |
| 软件发现与推荐 | 已有用户明确需要发现新软件，且有可维护的索引来源与筛选质量方案 |
| GitLab/Codeberg 等来源 | 现有用户提出具体来源需求，Release/附件契约与验证边界已明确 |
| 内置 AI 摘要或语义检索 | 外部 Agent 方案不能满足桌面用户需求，且模型配置、成本和可核查来源有明确方案 |
| 自动安装与实际安装版本检测 | 明确选择进入软件管理领域，另立安装状态、权限与兼容性方案 |
| 跨平台、私有仓库、远程服务 | 分别验证实际需求、认证/文件归属和运维成本，不与首版原生插件或后续本地 MCP 捆绑 |

**6. 共用能力与实现边界**

建议的数据流：桌面界面或 Agent → 受控操作入口 → 同一 Catalog/Library/Manager/Engine → 同一队列与存储。

复用当前 Rust 核心，先围绕 M2A 的原生插件必需操作建立窄接口并验证语义；M2B 的 MCP 适配器只转换协议与结果，不重新实现下载算法。业务能力保持在 GitHubSP 服务中，避免依赖 Harness 内部状态，以便其他 Agent 后续独立接入。未来需要独立运行时再调整宿主生命周期。

M1 的偏好、M2A 的幂等信息及 M3 的更新记录可能需要扩展持久化。每阶段先明确兼容、迁移与备份恢复方式，再实施；M2B 复用已验证的数据与操作契约，数据库版本和公共接口在方案审阅阶段不冻结。

不让已下载字节、长篇日志或完整 HTML 占用 Agent 上下文。常规返回结构化摘要，按需读取详情；结果中包含来源和不确定性。工具超时、连接断开和用户取消分别处理。

**7. 已确定顺序与其余审阅取舍**

Agent 接入顺序已确定为 M2A 原生插件 → 真实验收和使用检查 → M2B MCP。后续新增 Agent 能力也遵循先在 Harness 插件验证、再封装或同步到 MCP 的顺序。

初稿建议近期先做 M0、M1 和 M2A；之后用户授权完成全部阶段，实际按 M0 → M1 → M2A 验收 → M2B → M3 → M4 实施。各阶段新增 Agent 能力继续先原生验证再同步 MCP。第 5 节后续候选未自动进入本轮范围。

以下保留原审阅取舍；本次按“本稿建议”列实施，运行条件和边界见交付说明。将来调整这些条件时再评估工作量：

| 审阅项 | 本稿建议 | 调整后的影响 |
| --- | --- | --- |
| 软件本体与 Agent 的侧重 | 先完善共用能力，同时尽早试接 Harness 原生插件 | 若 Agent 优先，可将 M1 的网络设置后移，先复用现有下载能力验证 M2A |
| 原生插件首版运行条件 | 依赖 GitHubSP 正在运行，可最小化到托盘；MCP 后续复用 | 若首版要求完全无界面，需前置工作进程拆分及生命周期验收，M2A 投入提高 |
| 关注的首期范围 | 本地 Release 关注与处理记录 | 若需要 GitHub Star/Watch 同步，需增加账号、远程写入及冲突规则 |
| 下一轮边界 | 下载与持续关注；安装管理后续单独决定 | 若加入安装，需重新评估目标、状态模型和整体计划 |

**8. 调研依据与适用边界**

- [GitHub CLI：Release 下载](https://cli.github.com/manual/gh_release_download)、[Release 附件来源验证](https://cli.github.com/manual/gh_release_verify-asset)：基础下载与验证已有官方命令。

- [OpenAI：插件包装](https://developers.openai.com/plugins/build/plugins)、[Skills 与 MCP 的分工](https://developers.openai.com/plugins/concepts/skills)：协议能力与工作流包装可逐步交付。
- [Claude Code：插件](https://code.claude.com/docs/en/plugins)、[定时任务](https://code.claude.com/docs/en/scheduled-tasks)：工具调用与持续调度是不同能力。
